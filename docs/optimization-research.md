# Исследование оптимизаций V100

> По материалам статьи [Выжать больше из локальных LLM](https://habr.com/ru/articles/1025132/) (Хабр, 2026-04-24)

## Ключевые рекомендации статьи

### 1. ncmoe вместо ngl для MoE моделей

**Суть:** MoE модели разрежены — не все эксперты активируются на каждом токене. При загрузке целыми слоями (ngl) GPU простаивает, т.к. «дыры» от неактивных экспертов занимают VRAM без пользы. Режим ncmoe (n-cpu-moe) перераспределяет тензоры точечно, загружая GPU на 100%.

**Режимы:**
- `-ngl` / `--n-gpu-layers` — загрузка целыми слоями (стандарт)
- `-ncmoe` / `--n-cpu-moe` — точечное распределение тензоров для MoE
- `-cmoe` / `--cpu-moe` — MoE-эксперты на CPU, остальное на GPU

**Наша ситуация:** Мы используем `--fit on`, который **автоматически включает ncmoe** для MoE моделей. Оптимизация УЖЕ применена.

**Статья:** llama.cpp с ncmoe на RTX 4060 16GB даёт 45 tok/s vs ollama с ngl 16 tok/s (**2.8× быстрее**).

### 2. UD-Q4_K_XL лучше Q4_K_M

**Суть:** Unsloth Dynamic (UD) квантование использует:
- Блочное квантование с разными scale для каждого блока
- Калибровочную imatrix для определения значимости тензоров
- Повышенное квантование attn-тензоров (категория XL = Extra Large quality для attention)

**Результаты статьи (Qwen3.6-35B-A3B):**
- Q4_K_M ≈ UD-Q3_K_XL по качеству (но UD-Q3_K_XL легче на 4.4 GB!)
- UD-Q4_K_XL лучше Q4_K_M, но тяжелее на 1.2 GB
- UD-Q2_K_XL при равном весе лучше IQ2_M

**Для нашего стека:** Мы используем Qwen3.5-122B-A10B **Q4_K_M** (72 GiB). Если unsloth выпустит UD-Q4_K_XL для этой модели, можно получить лучшее качество при аналогичном или чуть большем размере.

**Статус:** Проверить наличие UD-Q4_K_XL для Qwen3.5-122B-A10B на HuggingFace (unsloth).

### 3. Параметры -b/-ub для ускорения PP

**Суть:** Prompt processing (PP) ускоряется увеличением batch/ubatch размеров. По умолчанию llama.cpp использует保守ные значения.

**Результаты статьи:**
| Конфигурация | PP speed |
|---|---|
| Без -ub/-b | 93 tok/s |
| `-ub 4096 -b 4096` | **475 tok/s** (**5.1×**) |

**Важно:** Увеличение -ub/-b требует больше VRAM. На 4060 Ti 16GB разница составила ~3 GiB.

**Для нашего стека (3× V100 32GB):** Добавлено `--batch-size 2048 --ubatch-size 2048` в stack.env. VRAM бюджет позволяет (GPU0 на 95.8%, но -b/-ub влияет только на compute buffer, не на постоянный allocation).

**Статус:** Реализовано в D-031.

### 4. ik_llama.cpp — форк с продвинутыми квантами

**Суть:** Форк llama.cpp от ikawrakow (создатель K-quants и I-quants). Основные преимущества:
- IQK кванты (IQ4_KS) — лучше качество при меньшем размере vs UD-Q4_K_XL
- Q6 квантование KV-кеша (между Q8 и F16)
- Лучшая скорость PP (в 4× при стандартных -ub/-b)
- Медленнее падает PP на длинном контексте

**Минусы:**
- TG скорость может быть **ниже** llama.cpp, особенно для IQK квантов
- Один разработчик — расхождение с llama.cpp растёт
- Нет нормальной поддержки Vulkan/ROCm
- Нет поддержки mxfp4 (в 2-3× медленнее)
- Нужна отдельная сборка под CC 7.0 (V100)

**Для нашего стека:** Требует сборки под CC 7.0 (Volta). Интересно в первую очередь для IQ4_KS квантов (лучшее качество при том же размере) и Q6 KV cache.

**Статус:** Отложено. Требует сборки и тестирования.

### 5. Speculative decoding (повторение)

**Суть:** Маленькая модель-черновик генерирует N токенов, большая модель верифицирует. Ускорение ~1.5× для Dense моделей на коде.

**Для нашего стека:** **НЕ ПРИМЕНИМО**. Гибридные SSM модели (Qwen3.5-122B, Qwen3.6-35B) не поддерживают speculative decoding — SSM/recurrent слои не позволяют откатить KV-state при rejected tokens (D-016).

### 6. REAP — pruning MoE экспертов

**Суть:** Router-weighted Expert Activation Pruning — удаление наименее активных экспертов для сценария использования. REAP20 удаляет 20%.

**Для нашего стека:** Рискованно. Удаление экспертов может ухудшить качество на задачах вне coding scope. Наши модели уже оптимизированы по размеру (10B active из 122B total).

**Статус:** Не рекомендуется.

## Примечания

- Все оптимизации нужно тестировать на **одном и том же бенчмарке** (10 задач из `evals/benchmark-suite.json`)
- Каждое изменение: `bash scripts/stack.sh restart && bash scripts/stack.sh smoke`
- Замерять decode speed + PP speed до и после
- Сравнение «до/после» в формате таблицы
